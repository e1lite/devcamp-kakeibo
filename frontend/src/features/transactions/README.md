# features/transactions

取引の画面（SCR-010 取引一覧・SCR-011 取引登録・SCR-012 取引詳細・SCR-013 取引編集）で使う処理。

| ファイル | 役割 |
|---|---|
| `listQuery.ts` | 取引一覧の絞り込み条件。URL のクエリ ↔ API-010 に渡す値の変換 |
| `hooks/useTransactionList.ts` | 取引一覧の取得。**API-010 を呼ぶのはここだけ** |
| `form.ts` | 登録・編集フォームの検証と、API-011 / API-013 に送る値の組み立て |
| `components/` | 取引の画面だけで使う部品（絞り込み・一覧の行・ページ送り・フォーム） |

## 画面の側に `useEffect(() => fetch(...))` を書かない理由

取引一覧の絞り込み（期間・カテゴリ・決済手段・キーワード・店舗・ページ送り）は、
**すべて URL のクエリを書き換えるだけ**にしている（Step 5 のイベント設計の方針 #1）。
API-010 を呼ぶのは `useTransactionList` の「URL が変わったら取得する」の 1 か所だけ。

```
操作（期間を変える・カテゴリを選ぶ・ページを送る …）
  └─ router.push(toListHref(withFilter(query, 変更)))   … URL を書き換えるだけ
        └─ useSearchParams が変わる
              └─ useTransactionList(query)               … ここだけが API-010 を呼ぶ
```

画面の部品ごとに `fetch` を書くと、次のことが起きやすい。

- **呼び出しが重なる**: 期間を変えたときとページを送ったときで、別々に API を呼ぶ処理ができる。
  条件の組み合わせ（期間 × カテゴリ × ページ）ごとに、正しい値で呼べているかを確かめる箇所が増える
- **古い結果で上書きされる**: 素早く条件を変えると、先に出した要求の結果が後から届くことがある。
  ここでは取得の途中で条件が変わったら前の要求を中断し、結果を捨てている（`AbortController`）
- **URL と画面がずれる**: ブラウザの「戻る」「進む」や、取引詳細の「この店舗の取引を見る」から来たときも、
  URL さえ正しければ同じ処理で同じ一覧になる

新しい絞り込みを足すときは、`listQuery.ts` の `PARAMS` に URL のクエリ名を足し、
画面では `withFilter` で URL を書き換える。API を呼ぶ処理は増やさない。
