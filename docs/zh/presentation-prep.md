## 2. ER 图怎么讲（用「中核部分の ER 図」那张）

按数据流走，别按表名念：

```
mail_accounts     ← 连了哪个邮箱
  ↓ P1 收集
email_messages    ← 原始邮件，不删。Gmail message ID 加 UNIQUE 保证幂等
  ↓ P3 抽出（1通 → N件）
payment_events    ← 从邮件抽出的支付事件
  ↓ P5 名寄せ（N件 → 1笔）
transactions      ← 实际的一次消费
  ↓ P6 分类
categories
```

**必须强调的两处多重度**（教材点名要讲リレーション設計）：

| 关系 | 多重度 | 一句话理由 |
|---|---|---|
| `email_messages` → `payment_events` | **1 — N** | 银行的汇总通知、卡的月度确定明细，**一封邮件里有好几笔** |
| `transactions` → `payment_events` | **1 — N** | 同一笔购买，**电商和卡会各发一封邮件**，要束成一笔 |

日文说法：
> 1 通のメールから複数の決済が読み取れるケースがあるので 1 対 N です。
> 逆に、同じ買い物が EC とカードの両方からメールを発生させるので、
> 複数のイベントを 1 つの取引に束ねる必要があります。

## 3. 十条設計判断（讲三条就够，剩下备着被问）

### ⭐ 优先讲这三条

**① 三层分割 —— 为了能重算**
> 生データを消さずに保持しているので、抽出や名寄せのロジックを変えたときに全件を再計算できます。
> 逆に言うと、メールから直接取引を作る設計にすると、閾値を 1 回調整するだけで
> Gmail から取り直しになってしまいます。

**② 为什么不用中间表 —— 这条最能体现「想过」**
> 最初は `payment_events` と `transactions` を多対多だと考えて中間テーブルを置いていました。
> ですが、**1 つの決済イベントが属する取引は必ず 1 つ**なので、実際は N 対 1 です。
> 中間テーブルをやめて `payment_events.transaction_id` の外部キーにしました。
> マージ解除も、この列を NULL に戻すだけで実現できます。

👉 这条是**主动说出「我原本想错了，后来改对了」**，比一开始就对更有说服力。

**③ `event_type` 一个列干两件事**
> `payment_events.event_type` は、名寄せ後にどの金額を採用するかの判定と、
> 即時通知を送るかどうかの判定の**両方で使っています**。
> EC の注文確認で通知してしまうと、数日後のカード利用速報で同じ買い物が二重に通知されるためです。

### 剩下七条（被问到再答）

| # | 判断 | 一句话 |
|---|---|---|
| ④ | `transactions` 有自己的字段 | 不引用「代表事件」，否则重算会抹掉用户的手改。用 `is_user_edited` 保护 |
| ⑤ | `merchants` 按支店 + `brand_name` 列 | 地图要支店粒度，汇总和分类规则要品牌粒度。没拆 `brands` 表是范围取舍 |
| ⑥ | `notifications.dedupe_key` | 一个 `UNIQUE(user_id, dedupe_key)` 同时防住三种通知的重复发送。因为批处理 1 分钟跑一次 |
| ⑦ | `extraction_rules` 用 jsonb | 每个发件人要抽的字段不一样，用列会全是 NULL 且加字段就要迁移。但**判定条件用列**，因为要检索 |
| ⑧ | 金额用 `bigint` 最小单位 | 避免浮点误差。外币存「原货币 + 原金额 + 日元换算」 |
| ⑨ | 多租户设计 | 运营是单用户，但所有业务表带 `user_id`。事后加代价太高 |
| ⑩ | 认证分两层 | 调 API 的权限（JWT）和读邮件的权限（Google OAuth）目的和有效期都不同，后者绝不用于 API 请求 |

## 4. 索引怎么讲（教材点名要「インデックス選定」）

别一条条念，按**四种用途**归类讲：

| 用途 | 例子 | 说法 |
|---|---|---|
| 画面主导线 | `(user_id, occurred_at DESC)` | 「取引一覧は期間で絞って新着順が基本操作なので」 |
| **算法专用** | `(user_id, amount_jpy_minor, occurred_at)` | 「**名寄せの候補生成専用**です。金額一致 + 日時近接で絞るため」 |
| 批处理取队列 | `parse_status`, `geocode_status`, `notified_at IS NULL` | 「該当行が少ないので**部分インデックス**にしています」 |
| 每次都要查的 | `merchant_aliases (user_id, alias)` | 「メール 1 通ごとに必ず引くので、一番呼ばれます」 |

👉 **「算法专用索引」这个说法很加分** —— 说明你不是套模板，是按实际查询设计的。

## 5. 「迷った点」怎么讲（教材明确要求，别跳过）

**讲纠结比讲结论加分。** 挑两三条：

1. **`sync_jobs` 的粒度**
   > 即時通知のために 1 分間隔で回すので、そのままだと 1 日 1440 行になります。
   > 変化がなかった実行は記録しない方針にしましたが、
   > それだと「バッチが動いているか」の確認ができなくなるので迷いました。

2. **`merchants` 要不要拆 `brands` 表**
   > 正攻法は分けることだと思いますが、テーブル数と実装期間を考えて列で持ちました。

3. **邮件正文存不存**
   > 再解析のためには本文が必要ですが、個人の決済情報を保持することになるので迷っています。

4. **`transactions.status`（速报 / 确定）**
   > カード利用速報と確定明細で金額が変わることがあります。
   > 状態列を持つか、確からしさの高いイベントで上書きするかを決めきれていません。

## 6. メンタリング報告 C-1：讲座回顾（5 要素 × 3 观点）

⚠️ **如果你没做完这 7 章，就老实说没做完** —— 别硬讲，会被追问细节。
教材本身也写了「すでに同等の知識がある場合はスキップしても構いません」。

要讲的话，每个要素按「概要 / 能做什么 / 注意点」三段：

| 要素 | 概要 | 能做什么 | 注意点 |
|---|---|---|---|
| **DB 操作** | `database/sql` + driver 连 PostgreSQL | 用 `sql.DB` 做 CRUD，`Query`/`Exec`/事务 | `rows.Close()` 忘了会泄漏连接；`sql.DB` 是连接池不是单连接，别每次新建 |
| **Gin** | HTTP 路由框架 | 路由分组、中间件（认证 / 日志）、`ShouldBindJSON` 做参数绑定和校验 | 中间件顺序决定执行顺序；`c.Abort()` 不调的话后续 handler 还会跑 |
| **GORM** | ORM，结构体 ↔ 表 | 自动迁移、关联（`Preload`）、钩子 | **N+1 查询**是最常见的坑，关联要用 `Preload`；`AutoMigrate` 不会删列，生产环境要用迁移工具 |
| **静的解析** | `golangci-lint` | 一次跑多个 linter（`govet` / `staticcheck` / `errcheck`） | 全开会淹在告警里，要在 `.golangci.yml` 里挑；**CI 里跑才有意义** |
| **自动测试** | 标准 `testing` 包 | 表驱动测试、`httptest` 测 handler、`t.Run` 分子测试 | 依赖 DB 的测试要么用 testcontainers 要么抽接口 mock；`t.Parallel()` 要注意共享状态 |

**结合自己项目讲会更好**，例如：
> 名寄せのスコアリングは純粋な関数なので、テーブル駆動テストが書きやすいと思っています。
> 逆に Gmail 取込の部分は外部依存なので、インタフェースを切ってモックする必要があります。
