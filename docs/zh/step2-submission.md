### ④ 設計判断 讲了什么

| 教材要求的点 | 我写的内容 |
|---|---|
| **表拆分** | 三层分割（`email_messages` / `payment_events` / `transactions`）。理由是逻辑改了要能全量重算，否则调一次名寄せ阈值就得重新拉 Gmail |
| **关系设计** | ① 一封邮件 1 对 N 支付事件（银行汇总通知）② 一笔交易 1 对 N 支付事件（电商和卡各发一封）③ **中间表原本以为要、后来发现是 N 对 1 所以砍掉了** ④ `transactions` 持有自己的字段以保护用户手改 |
| **删除的设计**<br>（新增小节） | ① **只有 `transactions` 改成逻辑删除** —— 物理删除会让事件回到未处理状态，下次批处理**把删掉的交易又生成一遍** ② 合并来源也不物理删除（用 `merged_into_id`），否则 `unmerge` 撤销不了、`409` 也判断不出来 ③ 解除邮箱连携用 `status='disabled'`，否则 CASCADE 会删光邮件原始数据 ④ **主数据保持物理删除** —— 逻辑删除会占着 `UNIQUE(user_id, name)` 让用户没法同名重建 |
| **endpoint 粒度** | ① `merge`/`unmerge`/`classify` 有副作用，所以做成动作型而不是通用 PUT ② 副作用用 `meta` 返回给用户看 ③ 批处理相关的 API 做到最少 ④ **`DELETE` 的含义逐个 endpoint 定义**，API 规格书里有对照表 |
| **索引选定** | 按 4 种用途分：画面主导线 / 聚合查询 / **算法专用（名寄せ 的候选生成）** / 批处理取队列（用部分索引）。另外 `merchant_aliases` 因为每封邮件必查所以优先。画面主导线那条现在是**部分索引 `WHERE deleted_at IS NULL`**，删除件数增加也不会让索引变胖 |
| 其他 | 金额用 bigint、`event_type` 一列干两件事、`dedupe_key` 防重复发送、多租户、认证分两层 |

### ⑤ まとめ 讲了什么

**辛苦的地方**
- 名寄せ 怎么建模最难。以为「金额 + 时刻 + 店名」三个一致就行，实际三个都对不上（发货时扣款、积分抵扣、收单方描述符）。所以改成打分 + 阈值三分支，并且**误合并比漏合并更糟**，阈值往保守倒
- 「没有输入界面的 app」怎么设计。样例 sns-camp 的数据来自用户输入，我的来自外部邮件，所以 UI 是「改机器错误的地方」而不是「输入的地方」。想通这点之前一直在照着普通记账 app 画界面

**纠结的地方**
1. `sync_jobs` 的粒度 —— **已经定了方案**（成功时即使 0 件也更新 `last_synced_at`，死活监视靠这一列）。剩下的顾虑是执行历史断断续续，排查故障会不会不方便
2. `merchants` 要不要拆 `brands` 表
3. 邮件正文存不存（重解析 vs 隐私）
4. 速报和确定明细金额不一致怎么处理

**学到的**
1. **先理清流水线再设计表和 API，迷茫会少很多。** 一开始从表入手，中途卡住；退回去把工序一道道写清楚后，表和画面几乎自动就定下来了
2. **多重度要能用话讲明白才算确认过。** 自问「一条支付事件会属于两笔交易吗？」，答案是不会，于是把多对多改成了 N 对 1
3. **索引不只是给画面用的。** 名寄せ 的候选生成是用户看不见的批处理，但它的性能由索引决定，要从实际查询的形状倒推着设计
4. **删除不只是「把行去掉」。** 物理删除交易会让支付事件回到未处理状态，下次批处理又生成一遍。光看表定义发现不了，只有把「批处理会反复跑」这个前提和外键的 `ON DELETE` 放一起看才能看出来。删除的设计要从数据的整个生命周期去想
