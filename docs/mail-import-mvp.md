# メール取込の最小版（計画）

テーマ: [決済メール解析による自動家計簿サービス](./theme-kakeibo.md)
位置づけ: **提出物ではない**。拡張フェーズのうち、メールの取込だけを先に通すための作業計画（2026-10-13 作成。同日に 1 章の 1〜3・5 まで実装。11 章）。

> このドキュメントで決めること
> 1. メールの取込を **どこまで作れば「最小版」と言えるか**（完成の定義）
> 2. 仕様書（[パイプライン](./step0-pipeline.md)・[DB 仕様書](./step2-db-spec.md)・[API 仕様書](./step2-api-spec.md)）から **何を省くか**
> 3. **どの順番で、いつ作るか**

---

## 0. なぜ今この計画が必要か

- Step 3 で範囲を「コア」（手入力の家計簿・カテゴリ・ログイン）に絞り、メールの取込は「Step 8 以降（拡張）」とした。
- しかし講座の Step 7〜12 は **インフラ・コンテナ・CI/CD・非機能要件** で、機能を作る Step が無い（Step 8 は「インフラ2」）。
  「Step 8 以降」は本リポジトリで付けたラベルにすぎず、何もしなければ取込を作る時間がどこにも無い。
- 取込が無いと、テーマの中心である「メールから家計簿が自動でできる」を発表で見せられない。

→ **Step 6 のコアを終えたあと、Step 7 と並行して最小版を作る。**

## 1. 完成の定義（デモの流れ）

次の 5 つが通れば最小版の完成とする。

| # | 操作 | 期待する結果 |
|---|---|---|
| 1 | 設定 → メール連携で「Gmail を連携」を押す | Google の同意画面を経て、連携の一覧に自分の Gmail が出る |
| 2 | 「今すぐ同期」を押す（初回は過去 3 か月を取得） | 対象のカード会社の利用通知が取引として取り込まれる |
| 3 | 取引一覧を開く | 取り込まれた取引が「未分類」で並び、カテゴリを付けられる |
| 4 | カードで買い物をしてから、もう一度「今すぐ同期」 | 取引が 1 件増える |
| 5 | 続けてもう一度「今すぐ同期」 | **件数が増えない**（同じメールを二重に取り込まない） |

## 2. 範囲

### 2.1 作るもの

| 工程（[パイプライン](./step0-pipeline.md) 2 章） | 最小版でやること | 仕様からの簡略化 |
|---|---|---|
| P0 認証・連携 | API-029 / API-030 で Gmail（`gmail.readonly`）を連携し、リフレッシュトークンを暗号化して `mail_accounts` に保存 | なし |
| P1 収集 | API-008 の手動同期（`incremental` / `backfill`）で取得し、`email_messages` と `sync_jobs` に記録 | **定期実行（1 分間隔）は作らない。** 取得はテンプレートの送信元だけに絞る（3 章 判断 2） |
| P2 判定 | `parser_templates` の送信元・件名と照合 | テンプレートは全ユーザ共通の 1〜2 件だけ（初期データとして投入） |
| P3 抽出 | テンプレートの正規表現で日時・金額・店舗名・カード下 4 桁を取り出し、`payment_events` を作る | 1 通から複数件を出すテンプレートは扱わない |
| P4 正規化 | 金額を円の整数に、日時を JST に。店舗名は文字幅などを揃えて `merchants` を名前で引き、無ければ作る。決済手段はカード下 4 桁で引き、無ければ作る | **`merchant_aliases`（表記ゆれ）は作らない** |
| P5 名寄せ | しない。**決済イベント 1 件 = 取引 1 件** | 3 章 判断 3 |
| P6 分類 | しない。カテゴリは「未分類」（`NULL`）のまま | 利用者が取引編集で付ける |

| 種類 | 対象 |
|---|---|
| API | API-006（連携一覧）、API-008（手動同期）、API-009（同期履歴。画面では最新 1 件だけ使う）、API-029・API-030（連携の開始・コールバック） |
| 画面 | SCR-050 メール連携（最小版。6 章）、設定メニューへのリンク |
| 余力があれば | API-007（連携解除）、SCR-012 取引詳細の「元になったメール」（API-012 の `payment_events[]` を埋める） |

### 2.2 作らないもの

| 対象 | 理由 |
|---|---|
| 定期実行（1 分間隔のポーリング）・Push 通知 | 手動同期でデモは成立する。実行基盤（常駐か EventBridge か）はインフラの Step と一緒に決める（パイプライン 6 章 未決事項 6） |
| 名寄せ・疑似重複の確認（SCR-040、API-015 / 016） | 最難関の工程。最小版はテンプレートを 1 種類に絞ることで重複が起きないようにする |
| 未判定メールの教示（SCR-041、API-017 / 018） | 送信元を絞って取得するため、未判定のメールがほぼ溜まらない |
| 表記ゆれ・店舗管理（`merchant_aliases`、SCR-042） | 1 社のメールだけなら店舗名の揺れは小さい |
| 分類ルール・学習（`category_rules`、`learn_category`） | 未分類のまま取り込み、手で付ける |
| 即時通知・月次サマリ・予算・サブスク・ジオコーディング | 取込が動いてからの工程 |
| 同期履歴画面（SCR-051） | 最新の同期結果は SCR-050 に出す |
| LLM によるテンプレート生成 | テンプレートは手で書く。社内ポリシーの確認も未了（パイプライン 6 章 未決事項 8） |

## 3. 主な設計判断

| # | 判断 | 理由・代償 |
|---|---|---|
| 1 | **取込方式は Gmail API に決める**（パイプライン 6 章 未決事項 1 を確定） | API-029 / 030 と `mail_accounts` がこの前提で設計済み。GAS は Go の外に部品が増え、IMAP はアプリパスワード（2 段階認証が前提）を扱うことになる。**代償**: OAuth アプリを「テスト」状態のまま使うため、リフレッシュトークンが **7 日で失効する**。そのため再認証（`reauth_required`）は最小版に含める |
| 2 | **取得するのはテンプレートの送信元のメールだけ**（`messages.list` に `from:(…) after:…` の検索条件を付ける） | 仕様は受信箱全体を `history.list` で差分取得し、P2 で判定する設計。最小版は先に送信元で絞る。**利点**: 決済と無関係なメールをサーバに保存しない。件数が少なく同期がすぐ終わる。**代償**: テンプレートに無い送信元の決済メールは取り込めない。SCR-041（教示）は全件取得が前提のため、拡張するときに `history.list` へ切り替える |
| 3 | **名寄せをしないかわりに、テンプレートは「カードの利用通知」1 種類に絞る** | EC の注文確認とカードの利用通知を両方入れると、同じ買い物が 2 件になる。手入力した取引と重なる可能性は残るが、P5 名寄せの位置づけとして発表で説明できる |
| 4 | **同期は API サーバの中の goroutine で実行する**（API-008 は仕様どおり `202` を返す） | 別のワーカーを作らない。同じ連携の二重実行は `sync_jobs` の `running` の行で判定して `409`。再起動で `running` のまま残ったジョブは起動時に `failed` にする。サーバを複数台にするときは見直す（ログインの `state` と同じ制約） |
| 5 | **差分取得の起点は「前回成功した同期の開始時刻 − 1 日」** | `sync_cursor`（`historyId`）は使わない。期間を重ねて取得しても、`UNIQUE(mail_account_id, provider_message_id)` で同じメールは 1 行にしかならない |
| 6 | **`state` に用途（ログイン / メール連携）とユーザ ID を持たせる** | ログイン用の `state` を API-030 で使い回させない（API-029 の「サーバ側で行うこと」）。今の `StateStore` は戻り先しか持っていないため拡張する |
| 7 | **`prompt=consent` は有効なリフレッシュトークンが無いとき（新規・`reauth_required`・`disabled`）だけ付ける** | Step 4 のフィードバック。`active` の連携をやり直すたびに同意画面を出さない |
| 8 | **リフレッシュトークンは AES-256-GCM で暗号化して保存する**。鍵は環境変数 `MAIL_CREDENTIAL_KEY` | レスポンス・ログには一切出さない（API-006 の注記） |
| 9 | **Gmail API は既存の `golang.org/x/oauth2` の HTTP クライアントで直接呼ぶ** | 使うのは `users.getProfile`・`messages.list`・`messages.get` の 3 つだけで、公式の大きなクライアントライブラリを足すほどではない。`httptest` でテストしやすい |
| 10 | **メールは `format=raw` で受け取り、標準の `net/mail`・`mime/multipart` で分解する** | 日本語のメールに残る ISO-2022-JP などは `golang.org/x/text` で変換する（パイプライン P3「日本語メール特有の処理」） |
| 11 | **取引の `status` は `pending`**（利用通知は速報のため。DB 仕様書 3.7） | 画面では出し分けない |

## 4. データベース

テーブルは **仕様書の定義のまま** 作る。最小版で使わない列は `NULL` のまま残し、拡張するときにマイグレーションを足さずに済むようにする。

| マイグレーション | テーブル | 備考 |
|---|---|---|
| 追加 | `sync_jobs`（3.3） | `trigger` は `manual` / `backfill` だけ使う |
| 追加 | `parser_templates`（3.5） | `email_messages` から参照されるため先に作る |
| 追加 | `email_messages`（3.4） | 本文（`body_text` / `body_html`）も保存する（3.4・6.4 の方針どおり） |
| 追加 | `payment_events`（3.6） | `link_type` は常に `auto`、`link_score` は使わない |
| 追加 | 初期テンプレートの投入 | `user_id = NULL`（全ユーザ共通）で 1〜2 件 |

作らないテーブル: `merchant_aliases`、`category_rules`、`notification_settings`、`notifications`、`subscriptions`、`budgets`、`monthly_summaries`。

> 番号は実装時に決める。Step 6 で「未分類」を `NULL` に移すマイグレーションを先に足すため。

## 10. リスク

| リスク | 対策 |
|---|---|
| リフレッシュトークンが 7 日で失効する | 再認証を最小版に含める。**発表の前日に連携し直す** |
| カード会社がメールの形式を変える | 抽出の失敗は `email_messages.parse_status = failed` と `sync_jobs.failed_count` に残るので、画面の同期結果で気づける |
| 個人のメール・決済データを扱う | 取得は送信元で絞る。テスト用データと発表のスクリーンショットでは個人情報を伏せる |

## 11. 実装の記録（2026-10-13）

### 結果

利用者の Gmail を連携し、過去 90 日の三井住友カード（Olive）の利用通知を取り込んだ。

| 項目 | 結果 |
|---|---|
| 取り込んだメール | 142 通 |
| 取引にしたもの | **139 件**（クレジット 120・デビット 19）。抽出の失敗は 0 |
| 取り込まなかったもの | 返品 2 通（理由を記録）、テンプレートに当たらないメール 1 通（dポイント） |
| 2 回目の同期 | 取得 0・取引 0（同じメールを二重に取り込まない） |

1 章の完成の定義のうち 1〜3・5 を確かめた。4（新しい利用のあとの同期）は、次にカードを使ったときに確かめる。

### 計画から変えたこと

| # | 変更 | 理由 |
|---|---|---|
| 1 | **テンプレートはマイグレーションではなくコード（`extract.BuiltinTemplates`）に置き、起動時にデータベースへ反映する** | 単体テストと実際の判定・抽出で同じ定義を使い、ルールとテストがずれないようにするため |
| 2 | **`extraction_rules` に `skip`・`payment_method`・`gmail_query` を足した** | 全ユーザ共通のテンプレート（`user_id = NULL`）は、ユーザごとの `payment_methods` を参照できない（`parser_templates.payment_method_id` が使えない）。決済手段は名前と種別で持ち、ユーザごとに作る。取り込まない条件（返品）と、Gmail の検索条件もテンプレートごとに持つ |
| 3 | **返品と外貨は取り込まない**（`parse_status = skipped`、理由を `parse_error` に残す） | 返品を支出として足すと二重に数える（元の取引との対応づけは名寄せ＝拡張）。外貨は円換算の為替レートの取得元が無い（手入力と同じ制限） |
| 4 | **最初は件名だけで探し、実際のメールを見てからテンプレートを作った** | 利用者のカード会社が決まる前に、取り込むメールを件名で絞って実物を確かめるため。テンプレートができてからは、送信元と件名の両方で探す（判断 2） |
| 5 | **連携ではアカウントの選択画面を毎回出す**（`prompt=select_account`。新規・再認証では `consent` も） | ログインしたアカウント（勤務先）と、連携する Gmail（個人）が違う。ブラウザがログイン中の別のアカウントで、黙って連携しないようにする |
| 6 | **Gmail API の 403 を、権限の問題と利用上限で分ける**。利用上限は待ってやり直し、連携は止めない | 初回の取込の途中で 403 を一律に「再認証が必要」と扱い、連携が止まった。原因を後から追えるよう、Google の理由をエラーの文言に残す |
| 7 | **判定・抽出は、取得が途中で失敗しても行う** | 保存済みのメールだけで行え、Gmail に繋がらなくてもできるため |
| 8 | デビットの決済手段の種別は `bank` | 利用と同時に口座から引き落とされるため |
