# イベント設計

サービス名: 決済メール解析による自動家計簿サービス
対応する画面一覧: [step4-screens.md](./step4-screens.md)
画面遷移図: [step4-transition.md](./step4-transition.md)
API 仕様書: [step2-api-spec.md](./step2-api-spec.md)（API ID はこの仕様書の番号）

> - 対象は **Step 6 で実装するコアの 9 画面と共通ヘッダー**。拡張の 10 画面は Step 8 で画面と合わせて追加する
> - SCR-001 / SCR-003 は表示を持たないが、**画面を開いた瞬間の処理がすべて**のため、イベント設計の対象に含める
> - 表の列は課題のサンプルに合わせ「イベント・トリガー・呼び出す API・表示・処理内容」とした。**API のエラーごとの挙動**は、画面ごとに 2 つ目の表に分けた
> - フロントは Next.js を **`localhost:5173`** で起動する（`next dev -p 5173`。バックエンドの `DEFAULT_REDIRECT_URI` に合わせる）。本書の「フロントのオリジン」はこの URL を指す
> - API は**ブラウザから同一オリジンの `/api/v1/...` を呼び**、Next.js の rewrites で `localhost:8080` へ転送する（API 仕様書 2 章の CORS）。トークンは `sessionStorage` に保存し（Step 4 判断 9）、`Authorization` ヘッダに付ける
> - トークンを HttpOnly Cookie に移す場合（Step 4 相談事項 2）も、**呼び出す API とタイミングは変わらない**。呼び出す場所がブラウザから Next.js のサーバ側に移るだけである
> - 関連 API のパスは共通の `/api/v1` を省略して書く。「なし」は API を呼ばないイベント

## 0. Step 4 からの変更（イベント設計で見つかったこと）

画面ごとに「いつ・どの API を・どんな値で呼ぶか」を 1 つずつ書いたところ、Step 4 の画面一覧・遷移図のままでは不都合な点が 7 件見つかった。

| # | 変更 | 理由 | 対象 |
|---|---|---|---|
| 1 | **API-004（ログイン中のユーザの確認）は共通レイアウトの 1 か所だけで呼ぶ。** SCR-001 / SCR-003 では呼ばず、トークンの有無だけで遷移する | Step 4 では SCR-001・SCR-003・共通ヘッダーの 3 か所で呼ぶ設計で、ログイン直後は SCR-003 → SCR-010 で 2 回呼ぶことになっていた。認証が必要な画面は必ず共通レイアウトを通るため、確認はそこに集めれば足りる（Step 4 判断 6「認証の扱いを全画面で共通にする」をイベントの単位まで進めた） | SCR-001 / SCR-003 / 共通 |
| 2 | **店舗で絞り込むとき（`merchant_id` があるとき）は、期間の既定を全期間にする** | 期間の既定は当月のため、SCR-012 の「この店舗の取引を見る」を先月の取引から押すと、**押した元の取引すら一覧に出ない** | SCR-010 / SCR-012 |
| 3 | **取引の編集でカテゴリを変えたときは `learn_category: false` を明示して送る** | API-013 の `learn_category` は省略すると `true`。Step 6 では「今後の同じ店舗にも適用する」のチェックボックスを出さないため、省略したままだと **Step 8 で学習を実装した時点で、画面に何の表示も無いまま学習が始まる** | SCR-013 |
| 4 | **決済手段の選択肢は `include_inactive=true` で取得する**（一覧の絞り込みでは全件を出し、編集では現在の値のときだけ利用停止中を残す） | API-031 は既定で利用停止中の決済手段を返さない。そのままでは過去の取引を絞り込めず、編集画面で現在の値を表示できない。コアの段階では `現金` のみのため影響は無いが、Step 8 でメールから決済手段が作られると起きる | SCR-010 / SCR-013 |
| 5 | **登録後は、登録した取引の月を期間にして一覧を開く** | 先月のレシートを入力して当月の一覧に戻ると、登録した取引が見えず、登録できたのか分からない | SCR-011 |
| 6 | **削除後・保存後にも完了メッセージを出す**（Step 4 は登録後のみ） | 削除後は一覧に戻るため、消えたことを確かめる手がかりが無い | SCR-012 / SCR-013 |
| 7 | **カテゴリの削除確認で、子カテゴリが最上位に移ることも示す** | API-021 の削除では子カテゴリの `parent_id` が `null` になる。取引件数だけを示すと、階層が崩れることに気づけない | SCR-020 |

## 1. 全画面共通

### 1.1 共通レイアウト（認証が必要な画面すべて）

SCR-001 / SCR-002 / SCR-003 / SCR-099 を除く画面は、この共通レイアウトの中に表示する。
Next.js の共通レイアウトは画面を移っても作り直されないため、#1 は**ページを読み込んだときに 1 回だけ**行われる。

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 認証の確認・ユーザの表示 | 認証が必要な画面を開いたとき（ページの読み込み・リロード） | API-004 `GET /auth/me`（トークンがあるときのみ） | トークンが無ければ API を呼ばず、開こうとしていた URL を戻り先として保存して SCR-002 へ。`200` ならヘッダーに表示名（`display_name`、`null` なら `email`）を出し、画面の中身を表示する。**API-004 が成功するまで画面の中身は出さない**（各画面の初期表示はその後に始まる） |
| 2 | 画面の切り替え | サービス名・ナビ「取引」押下 / 「設定」→「カテゴリ」押下 | なし | SCR-010 / SCR-020 へ |
| 3 | 設定メニューの開閉 | 「設定」押下 / メニューの外の押下・Esc | なし | メニューを開く / 閉じる |
| 4 | ログアウト | 「ログアウト」押下 | API-005 `POST /auth/logout` | **結果にかかわらず**トークンを破棄し、SCR-002 へ。戻り先は保存しない |

### 1.2 API の結果に対する共通の扱い

| API の結果 | 画面を開いたときの取得 | 登録・更新・削除の操作 |
|---|---|---|
| `401 INVALID_TOKEN` / `TOKEN_EXPIRED` | トークンを破棄し、今の URL を戻り先として保存して SCR-002 へ（`?error=<コード>`）。**複数の API が同時に `401` を返しても遷移は 1 回だけ** | 同左。入力中の内容は失われる（有効期限は 24 時間のため、入力中に切れるのはまれとして許容する）。**ログアウト（API-005）だけは例外**で、1.1 #4 のとおりエラーを出さずに SCR-002 へ移る（ログアウトしたいだけの人に「期限切れ」を見せないため） |
| `5xx`・通信エラー | 取得できなかった部分に「読み込めませんでした」と「再試行」ボタンを出す。「再試行」で同じ API を呼び直す | 画面上部にエラーを出し、**入力内容を保ったまま**ボタンを押せる状態に戻す |
| `400` / `403` / `404` / `409` | 画面ごとの表に記載 | 画面ごとの表に記載 |

- 登録・更新・削除の API を呼んでいる間は、そのボタンを無効にして「送信中…」と表示する（二重送信を防ぐ）
- 完了メッセージ（「登録しました」など）は、遷移先の画面の上部に数秒表示する。**一度だけ表示する**（リロードで再び出さない）
- 金額は `amount_minor` を `¥38,450` の形式で、日時は日本時間で `2026/09/09 12:31` の形式で表示する

## 2. 画面ごとのイベント

### SCR-001 ルート

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 振り分け | 画面表示時 | なし | トークンがあれば SCR-010、無ければ SCR-002 へ（履歴を置き換える）。トークンが有効かは、遷移先の共通レイアウト（1.1 #1）で確認する |

### SCR-002 ログイン

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 初期表示 | 画面表示時 | なし | トークンがあれば SCR-010 へ（履歴を置き換える）。無ければログイン画面を表示し、クエリに `error` があれば下表のメッセージを出す |
| 2 | ログイン開始 | 「Google でログイン」押下 | API-002 `GET /auth/google?redirect_uri=<フロントのオリジン>/auth/callback`（**fetch ではなくブラウザごと遷移**） | Google の同意画面へ移る。押した直後にボタンを無効にする |

| `error` の値 | 表示する文言 | 渡す元 |
|---|---|---|
| `ACCESS_DENIED` | Google でのアクセスの許可が必要です。もう一度ログインしてください | SCR-003（同意画面で拒否した） |
| `INVALID_STATE` / `VALIDATION_ERROR` | ログインをやり直してください | SCR-003 |
| `OAUTH_EXCHANGE_FAILED` | Google との通信に失敗しました。時間をおいてもう一度お試しください | SCR-003 |
| `TOKEN_EXPIRED` | ログインの有効期限が切れました。もう一度ログインしてください | 1.2 の `401` の扱い |
| `INVALID_TOKEN` | もう一度ログインしてください | 1.2 の `401` の扱い |
| 上記以外 | ログインに失敗しました。もう一度お試しください | - |

> 文言は上の表から選び、**クエリの文字列をそのまま画面に出さない**。任意の文言を表示させられると、偽の案内を出すフィッシングに使われるため。
> 期限切れのトークンが残ったまま #1 で SCR-010 へ移っても、共通レイアウトの `401` でトークンが破棄されて SCR-002 に戻るため、行き来が繰り返されることはない。

### SCR-003 ログイン処理中

表示は「ログインしています…」のみ。いずれのイベントも**履歴を置き換えて遷移する**（ブラウザの「戻る」でこの画面に戻らないようにするため）。

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | ログイン成功 | 画面表示時（フラグメントに `access_token` がある） | なし | `history.replaceState` でフラグメントを URL から消し、トークンを `sessionStorage` に保存する。戻り先があればそこへ、無ければ SCR-010 へ。戻り先は使ったら消す |
| 2 | ログイン失敗 | 画面表示時（フラグメントに `error` がある） | なし | フラグメントを消し、SCR-002 へ `?error=<コード>` を付けて遷移する |
| 3 | 不正な到達 | 画面表示時（どちらも無い。URL を直接開いたなど） | なし | SCR-002 へ |

> 戻り先は **`/` で始まり `//` で始まらないパスのときだけ**使う（Step 4 判断 7。外部サイトへのオープンリダイレクトを防ぐ）。

### SCR-010 取引一覧

**絞り込み条件は URL のクエリに持ち、クエリが変わったら一覧を取り直す**（Step 4 判断 5）。絞り込みの操作（#2〜#7）は URL を書き換えるだけで、API を呼ぶのは #1 に一本化する。

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 一覧の取得 | 画面表示時 / URL のクエリが変わったとき（絞り込みの変更、ブラウザの「戻る」「進む」を含む） | API-010 `GET /transactions`（下表の値）、API-019 `GET /categories`、API-031 `GET /payment-methods?include_inactive=true`。3 つを並行して呼び、同じ画面の中で条件を変えたときは API-010 のみ | 件数・合計金額と一覧を表示する。取得中は一覧の位置に「読み込み中」を出す。0 件なら「条件に合う取引はありません」（条件が無いときは「まだ取引がありません」）と「登録」ボタンを出す |
| 2 | 期間の変更 | 開始日・終了日を変えて欄から離れたとき | API-010（#1 経由） | URL の `from` / `to` を書き換え、`page` を 1 に戻す。開始日が終了日より後なら URL を変えず、欄の下に「開始日は終了日以前にしてください」 |
| 3 | カテゴリ・決済手段の選択 | プルダウンの変更 | API-010（#1 経由） | URL の `category_id` / `payment_method_id` を書き換え、`page` を 1 に戻す |
| 4 | キーワード検索 | 「検索」押下 / キーワード欄で Enter | API-010（#1 経由） | URL の `q` を書き換え、`page` を 1 に戻す。**1 文字入力するごとには呼ばない**（API の呼び出しとブラウザの履歴が入力のたびに増えるため） |
| 5 | 店舗の絞り込みの解除 | 「店舗: ○○ ×」押下（`merchant_id` があるときだけ表示） | API-010（#1 経由） | URL から `merchant_id` を外す |
| 6 | 条件のクリア | 「条件をクリア」押下 | API-010（#1 経由） | `/transactions`（当月 1 日〜今日）へ |
| 7 | ページ送り | ページ番号・「前へ」「次へ」押下 | API-010（#1 経由） | URL の `page` を書き換え、一覧の先頭までスクロールする |
| 8 | 詳細へ | 一覧の行を押下 | なし | SCR-012 へ |
| 9 | 登録へ | 「登録」押下 | なし | SCR-011 へ |
| 10 | 完了メッセージ | 画面表示時（SCR-011 / SCR-012 から完了の知らせがあるとき） | なし | 「登録しました」/「削除しました」を上部に表示する |

**URL のクエリと API-010 に渡す値**

| URL のクエリ | API-010 に渡す値 | クエリが無いとき |
|---|---|---|
| `from` / `to` | `from` / `to` | `merchant_id` が無ければ当月 1 日〜今日。**あれば渡さない（全期間）**（0 章 #2） |
| `category_id` | `category_id`（「未分類」は `none`） | 渡さない |
| `payment_method_id` | `payment_method_id` | 渡さない |
| `merchant_id` | `merchant_id` | 渡さない |
| `q` | `q` | 渡さない |
| `page` | `offset` = (`page` − 1) × 20、`limit` = 20 | `page` = 1 |

- カテゴリの選択肢は、先頭に「すべて」「未分類」を置き、続けて API-019 の順に並べる（子は親の下に字下げ）
- 決済手段の選択肢は、利用停止中のものも「（利用停止）」を付けて出す（過去の取引を絞り込めるように。0 章 #4）
- 店舗で絞り込み中の「店舗: ○○」の名前は、取得した一覧の `merchant.name` から取る
- **取得の途中で条件が変わったら、前の取得の結果は捨てる**（素早く条件を変えたとき、遅れて返った古い結果で一覧が上書きされないように）

| API の結果 | 画面の挙動 |
|---|---|
| API-010 `400 VALIDATION_ERROR` / `INVALID_DATE_RANGE` | URL を手で書き換えた場合などに起きる。一覧の位置に「条件が正しくありません」と「条件をクリア」ボタン |
| API-010 `200` で 0 件、かつ `page` が 2 以上 | 削除後に戻った場合などに起きる。「このページに取引はありません」と「1 ページ目へ」ボタン |
| API-019 / API-031 の失敗 | 該当するプルダウンだけを無効にして「再試行」を出す。一覧の表示は続ける |

### SCR-011 取引登録

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 初期表示 | 画面表示時 | API-019 `GET /categories`、API-031 `GET /payment-methods`（並行） | 入力フォームを表示する。初期値は日時 = 現在時刻、カテゴリ = 未分類、決済手段 = 現金（`kind = cash`）。選択肢がそろうまで「登録」ボタンを無効にする |

| 3 | 登録 | 「登録」押下 | API-011 `POST /transactions`（下表の値） | 送る前に #2 の検証をすべて行い、エラーがあれば呼ばない。`201` なら**登録した取引の月を期間にして** SCR-010 へ遷移し、「登録しました」を表示する（当月なら `/transactions`、それ以外なら `?from=<その月の 1 日>&to=<その月の末日>`。0 章 #5） |
| 4 | キャンセル | 「キャンセル」押下 | なし | 入力途中なら「入力内容を破棄しますか」の確認ダイアログを出す。破棄したら一覧へ戻る（履歴を戻る。履歴が無ければ SCR-010） |

|---|---|---|

| 金額 | `amount_minor` | 整数 |
| 店舗名 | `merchant_name` | 前後の空白を除く。空なら送らない |
| カテゴリ | `category_id` | 未分類なら送らない |
| 決済手段 | `payment_method_id` | 未選択なら送らない |
| メモ | `note` | 空なら送らない |
| （通貨） | `currency` | 送らない（サーバの既定の `JPY` になる） |

| API の結果 | 画面の挙動 |
|---|---|
| API-011 `400 INVALID_AMOUNT` | 金額欄の下に表示 |
| API-011 `400 VALIDATION_ERROR` | 画面上部に「入力内容を確認してください」 |
| API-011 `404 CATEGORY_NOT_FOUND` / `PAYMENT_METHOD_NOT_FOUND` | 画面上部に「選んだカテゴリ（決済手段）が見つかりません。選び直してください」。API-019 / API-031 を呼び直して選択肢を更新する（別のタブで削除された場合に起きる） |
| API-011 `400 UNSUPPORTED_CURRENCY` | 通貨を送らないため起きない |

### SCR-012 取引詳細

| API-012 `404 TRANSACTION_NOT_FOUND` | SCR-099「取引が見つかりません」（URL は変えない） |
| API-012 `403 FORBIDDEN` | SCR-099「この取引は表示できません」（URL は変えない） |
| API-014 `409 ALREADY_MERGED` | ダイアログ内に「マージを解除してから削除してください」（コアにはマージが無いため、通常は起きない） |
| API-014 `404 TRANSACTION_NOT_FOUND` | 別のタブで削除済み。「すでに削除されています」として #4 と同じく一覧へ戻る |
| API-014 `403 FORBIDDEN` | SCR-099「この取引は表示できません」 |

### SCR-013 取引編集

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 初期表示 | 画面表示時 | API-012 `GET /transactions/{id}`、API-019 `GET /categories`、API-031 `GET /payment-methods?include_inactive=true`（並行） | 取引の値を初期値にしてフォームを表示する。店舗名は表示のみ。利用停止中の決済手段は、**この取引の現在の値のときだけ**選択肢に残す（0 章 #4）。URL の `id` が数字でなければ API を呼ばず SCR-099（404） |
| 2 | 入力の検証 | 各入力欄から離れたとき | なし | SCR-011 #2 と同じ |
| 3 | 保存 | 「保存」押下 | API-013 `PUT /transactions/{id}` | **初期値から変わった項目だけを送る**（下表）。変更が無い間は「保存」を押せない。`200` なら SCR-012 へ戻り「保存しました」を表示する。ブラウザの「戻る」で編集画面に戻らないようにする |
| 4 | キャンセル | 「キャンセル」押下 | なし | 変更があれば「入力内容を破棄しますか」の確認ダイアログを出す。SCR-012 へ戻る |

| 変更 | 送る値 |
|---|---|
| カテゴリを未分類に戻した | `category_id: null` |
| 決済手段を外した | `payment_method_id: null` |
| メモを空にした | `note: null` |
| カテゴリを変えた | `category_id` に加えて **`learn_category: false`**（0 章 #3） |
| 上記以外 | 変えた項目の新しい値 |

| API の結果 | 画面の挙動 |
|---|---|
| API-012 `404` / `403` | SCR-012 と同じく SCR-099 |
| API-013 `400 INVALID_AMOUNT` | 金額欄の下に表示 |
| API-013 `400 VALIDATION_ERROR` | 画面上部に「入力内容を確認してください」 |
| API-013 `404 CATEGORY_NOT_FOUND` / `PAYMENT_METHOD_NOT_FOUND` | SCR-011 と同じ（画面上部に表示し、選択肢を取り直す） |
| API-013 `404 TRANSACTION_NOT_FOUND` / `403 FORBIDDEN` | 編集中に別のタブで削除された場合など。SCR-099 |
| API-013 `404 MERCHANT_NOT_FOUND` | 店舗を送らないため起きない |

### SCR-020 カテゴリ管理

作成・更新・削除のあとは、**画面上で一覧を書き換えるのではなく API-019 を呼び直す**。並び順・親子関係・取引件数をサーバの結果に合わせるためで、カテゴリは数十件のため取り直しても軽い。

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 一覧の取得 | 画面表示時 / #4・#5・#7 の成功後 | API-019 `GET /categories?include_counts=true` | 親の下に子を字下げし、`sort_order` 順に表示する。初期カテゴリ（`is_system`）には「初期」の印を付け、「削除」ボタンを出さない |
| 2 | 追加ダイアログを開く | 「追加」押下 | なし | 名前（空）・親（なし）・表示順（0）の入力ダイアログを開く |
| 3 | 編集ダイアログを開く | 行の「編集」押下 | なし | 現在の値を初期値にしたダイアログを開く。親の選択肢から**自分自身と子孫を除く**（サーバの `400 INVALID_PARENT` に頼る前に防ぐ） |
| 4 | 作成 | 追加ダイアログの「保存」押下 | API-020 `POST /categories` | 名前が空・51 文字以上なら API を呼ばず欄の下に表示する。`201` ならダイアログを閉じて #1 で一覧を取り直し、「追加しました」 |
| 5 | 更新 | 編集ダイアログの「保存」押下 | API-021 `PUT /categories/{id}`（変えた項目だけ。親を外すときは `parent_id: null`） | `200` ならダイアログを閉じて #1 で一覧を取り直し、「保存しました」 |
| 6 | 削除の確認 | 行の「削除」押下 | なし | 確認ダイアログを開く。`transaction_count` と子カテゴリの数を示す（「取引 12 件は未分類に、子カテゴリ 2 件は最上位に移ります」。0 章 #7） |
| 7 | 削除 | 削除ダイアログの「削除する」押下 | API-021 `DELETE /categories/{id}` | `204` ならダイアログを閉じて #1 で一覧を取り直し、「削除しました」 |
| 8 | ダイアログを閉じる | 「キャンセル」押下 / Esc | なし | ダイアログを閉じ、入力を破棄する |

| API の結果 | 画面の挙動 |
|---|---|
| API-020 / API-021 PUT `409 DUPLICATE_CATEGORY_NAME` | 名前欄の下に「同じ名前のカテゴリがあります」 |
| API-020 / API-021 PUT `400 VALIDATION_ERROR` | 名前欄の下に表示 |
| API-021 PUT `400 INVALID_PARENT` | 親の欄の下に表示（選択肢から除いているため、通常は起きない） |
| API-020 / API-021 PUT `404 PARENT_NOT_FOUND` | 親の欄の下に「親カテゴリが見つかりません」と出し、#1 で一覧を取り直す |

### SCR-099 エラー

| # | イベント | トリガー | 呼び出す API | 表示・処理内容 |
|---|---|---|---|---|
| 1 | 初期表示 | 存在しない URL を開いたとき / SCR-012・SCR-013 で API-012・API-013 が `404`・`403` を返したとき / 画面の処理で想定外の例外が起きたとき | なし | 種類に応じた文言を出す。`404`: 「ページが見つかりません」（取引の場合は「取引が見つかりません」）、`403`: 「この取引は表示できません」、想定外の例外: 「問題が発生しました」 |
| 2 | 一覧へ | 「取引一覧へ」押下 | なし | SCR-010 へ |

> API の `5xx` や通信エラーでは SCR-099 に移らず、1.2 のとおり**その画面の中で「再試行」できるようにする**。一時的な障害で、入力中の内容や見ていた画面を失わせないため。
