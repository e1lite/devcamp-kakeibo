## ③ 設計判断

### レイアウトの意図

| # | 判断 | 理由 |
|---|---|---|
| 1 | 主ボタン（塗りつぶし）は 1 画面に 1 つ | 画面の主な操作が一目で分かるようにする。PC は見出しの右、スマホは一覧なら画面下部、フォームなら末尾 |
| 2 | 一番知りたい数字を先に出す | 家計簿で最初に確かめたいのは「いくら使ったか」。一覧は件数と合計を一覧の上に、詳細は金額を最も大きな文字で出す |
| 3 | スマホでは一覧を表からカードに切り替える | 5 列の表は 360px に収まらず、店舗名と金額が読めなくなる |
| 4 | 削除は主ボタンから離し、確認ダイアログの初期フォーカスを「キャンセル」にする | 取り消せない操作を、押し間違いや Enter の連打で実行させない |
| 5 | 状態は、変わった領域の中で示す | 一覧の取得に失敗しても絞り込みは使えるように、画面全体を差し替えない |
| 6 | フォームは PC・スマホとも 1 列で、並びを幅によって変えない | 登録と編集、PC とスマホで入力欄の位置が変わらないので、一度覚えれば迷わない |
| 7 | 色だけで意味を伝えない | 速報・未分類・エラーは文字でも示す |

### 優先度

**画面の優先度**は、使う頻度で決めました。

| 優先度 | 画面 | 理由 |
|---|---|---|
| 高 | 取引一覧・取引登録 | 毎日開く画面。この 2 つだけスマホ版の図を描いた。手入力はレシートを手に持ったまま行うことが多いため、スマホの「登録」は親指の届く画面下部に固定した |
| 中 | 取引詳細・取引編集 | 自動分類の間違いを直すときに使う |
| 低 | カテゴリ管理・エラー | 使い始めにカテゴリを整えたあとは、たまにしか開かない |

**Step 6 の実装の順番**は、依存関係で決めます。

1. バックエンドの前提 4 件（イベント設計 4 章）。これが無いと、未分類の絞り込みや決済手段の選択肢が動かない
2. 認証まわり（SCR-001 / 002 / 003 と共通レイアウト）。ほかのすべての画面がこれを通る
3. 取引一覧 → 取引登録 → 取引詳細 → 取引編集。登録できないと一覧・詳細を確かめるデータが無いため、一覧の次に登録を作る
4. カテゴリ管理 → エラー

### 認証の想定

| 論点 | 判断 |
|---|---|
| トークンの保存先 | **`sessionStorage` のまま**（Step 4 判断 9。Step 4 のフィードバックで妥当と確認できた）。講座で学んだ HttpOnly Cookie へは将来移行しうるが、そのときは CSRF の対策（`SameSite=Lax` 以上と、状態を変える API での CSRF トークンの検証）が必要になり、ログイン直後に URL のフラグメントを消す処理は Cookie にしても残す。どちらにしても、呼ぶ API とタイミングは変わらない（イベント設計の前提） |
| 新しいタブ | `sessionStorage` はタブごとのため、新しいタブではログインし直しになる。ログイン画面で先に案内する（0 章 #14） |
| ログインの確認 | 共通レイアウトで API-004 を 1 回だけ呼び、成功するまで画面の中身を出さない（0 章 #1） |
| トークン切れ | どの画面のどの API が `401` を返しても、共通の処理でログイン画面へ送り、開いていた画面を戻り先として保存する。複数の API が同時に `401` を返しても遷移は 1 回だけ。ログアウトだけはエラーを出さない |
| ロールに応じた出し分け | **対象外**。本サービスの利用者は 1 種類で、ロールが無いため。他のユーザの取引は、存在しない取引と同じく「取引が見つかりません」と表示する（0 章 #12） |

### 状態管理の想定

| 状態 | 持つ場所 | 理由 |
|---|---|---|
| 取引一覧の絞り込み条件 | URL のクエリ | 詳細から「戻る」で条件が保たれ、条件つきの一覧へ直接遷移できる（Step 4 判断 5） |
| ログイン中のユーザ | 共通レイアウトの Context | 画面をまたいで共有する唯一の状態。ヘッダーの表示名に使う |
| 取引・カテゴリなどのデータ | 画面ごとに取得し、操作のあとは取り直す | 画面をまたいで共有するデータが少なく、キャッシュの整合を考えるより取り直す方が単純で確実。状態管理のライブラリは使わない |
| フォームの入力 | 画面内の state | 初期値との差分で「保存」を押せるかと、送る項目を決める |
| 完了メッセージ | 一度だけ読む印 | 遷移先で 1 回だけ表示し、リロードで再び出さない |

### イベント設計の方針

| # | 方針 | 例 |
|---|---|---|
| 1 | **API を呼ぶイベントを 1 つに集める** | 取引一覧の絞り込み（期間・カテゴリ・キーワード・ページ送り）はすべて URL を書き換えるだけにし、API-010 を呼ぶのは「URL が変わったら取得する」の 1 イベントにした |
| 2 | **「画面を開いたときの取得」と「操作」でエラーの扱いを分ける** | 取得の失敗はその領域に「再試行」、操作の失敗は入力を残したまま画面上部に表示 |
| 3 | **送る値まで決める** | 編集は変わった項目だけを送る。未分類に戻すときは `null`。カテゴリを変えたら `learn_category: false` |
| 4 | **画面で防げるものは API を呼ぶ前に防ぐ。ただしサーバの検証は外さない** | 親カテゴリの選択肢から自分と子孫を除く、開始日 > 終了日なら呼ばない |
| 5 | **非同期の競合を書いておく** | 古い取得結果を捨てる、送信中はボタンを押せなくする、`401` の遷移は 1 回だけ |

## ④ まとめ

### 苦労したこと

**状態のバリエーションの洗い出し。** 正常な画面を 1 枚描くのはすぐでしたが、1 画面ごとに「読み込み中・空・エラー・送信中・確認」を考えると、画面あたり 3〜6 個の状態が出てきました。特に**空の状態が 2 種類ある**ことに時間がかかりました。初めて使う人の「まだ取引がありません」と、絞り込んだ結果の「条件に合う取引はありません」では、次に取ってほしい行動（登録する / 条件を外す）が違うため、文言もボタンも分けました。

**Step 4 で済んだつもりだった点に、穴が見つかること。** 画面一覧の「主要な要素」の欄に「この店舗の取引を見る」と書いた時点では問題に見えませんでしたが、イベント設計で「そのとき API-010 にどの期間を渡すか」を書こうとして、既定の期間が当月であるために元の取引すら出ないことに気づきました（0 章 #2）。

### 判断に迷ったこと

- **他のユーザの取引を `403` と `404` のどちらで伝えるか。** Step 2 では「自分のデータでないことを明示する方が UI 上扱いやすい」として `403` を選び、Step 5 の最初の版でもエラー画面で「この取引は表示できません」と言い分けていました。Step 4 のフィードバックで、`403` を返した時点で「その ID の取引が存在する」ことが伝わると指摘を受けました。本サービスには共有の機能が無く、他のユーザの取引を開く正当な場面が無いため、言い分ける利点より漏れる情報の方が大きいと判断し、`404` に統一しました
- **例のデータをコア基準にするか、拡張後の基準にするか。** コアでは決済手段が現金のみ、取込元が手入力のみのため、その通りに描くと一覧の列の多くが同じ値になり、レイアウトの検討になりませんでした。拡張後のデータで描き、コアでの見え方は状態の図で別に示しました
- **Step 4 の文書を直すかどうか。** 0 章の変更を Step 4 の文書にも反映すると、提出時点で何を考えていたかが分からなくなります。Step 4 は提出時のまま残し、変更は Step 5 の記録として残しました（相談事項 2）

### 学んだこと

**既定値も画面の設計の一部であること。** `learn_category` の既定が `true`、決済手段一覧の既定が「利用中のみ」といった**省略したときの挙動**は、API 仕様書を書いた時点では API 側の都合で決めていました。画面から呼ぶ側に立つと、省略した値がそのまま画面の振る舞いになります。「何を送るか」と同じくらい「何を送らないか」を決める必要がありました。

**仕様書の値の一覧と、実際に入る値の組み合わせは違うこと。** 取引詳細で分類の由来を「手動」「自動分類」と出す設計にしていましたが、Step 3 の実装を見直すと、手入力でカテゴリを選ばなかった取引は由来が `default` になります。仕様書の値の一覧だけを見ていると「`user` 以外は自動分類」で済みそうですが、実際には「未分類なのに自動分類と表示される」組み合わせが起きていました。

**丁寧に伝えることが、そのまま情報を渡すことになる場合があること。** 「存在しない」と「見られない」を言い分けるのは利用者への親切のつもりでしたが、言い分けること自体が「存在する」という情報になっていました（0 章 #12）。エラーの文言は UX だけでなく、何を伝えてよいかというセキュリティの判断でもあります。

**前の Step の文書も、実装に合わせて直し続ける必要があること。** API-004 の `404` は Step 3 の実装で返らなくなっていたのに、仕様書に残ったままでした（0 章 #11）。Step 4 では「画面から見ると API の不足が見つかる」ことを学びましたが、今回は「後の Step から見ると、前の Step の文書が古くなっている」ことが分かりました。

## メンタリング報告

### 3.1 講座の振り返り

#### React の基本

| 観点 | 内容 |
|---|---|
| 概要 | UI を「状態から画面を作る関数」として書くライブラリ。画面を関数コンポーネントの組み合わせで作り、`props` で値を渡し、`useState` で状態を持つ。状態が変わると、その部分が描き直される |
| 何ができるのか | JSX で HTML に近い書き方ができる。入力欄・ボタン・ダイアログを部品にして使い回せる（取引の登録と編集で同じフォームを使う）。条件による表示の切り替えや、配列からの一覧の描画（`map`）ができる |
| 気をつけること | state を直接書き換えず、新しい値を作って渡す。一覧の `key` に配列の添字を使わない（削除や並べ替えで崩れるため、取引の `id` を使う）。件数や合計のように計算で出せる値を state に持たない。`useEffect` で取得するときは、**古い応答が新しい応答を上書きしない**ようにする（取引一覧で素早く条件を変えたとき） |

#### Next.js の基本

| 観点 | 内容 |
|---|---|
| 概要 | React のフレームワーク。`app/` 以下のフォルダ構成がそのまま URL になる（App Router）。サーバで描画する Server Components と、ブラウザで動く Client Components を使い分ける |
| 何ができるのか | `app/transactions/[id]/page.tsx` のような動的なルート。`layout.tsx` で共通レイアウトを作れ、**画面を移っても作り直されない**ため、ヘッダーと認証の確認を 1 か所に置ける（0 章 #1 の根拠）。`loading.tsx` / `error.tsx` / `not-found.tsx` で読み込み中・エラー画面を決まった場所に置ける。`next.config` の rewrites で `/api` を API サーバへ転送できる（API 仕様書 2 章） |
| 気をつけること | Server Components では `sessionStorage` や `useState` が使えない。今の設計（トークンを `sessionStorage` に置く）では、API を呼ぶ画面は Client Components になる。`useSearchParams` を使う画面は Suspense で囲まないとビルドで失敗する。履歴を積む遷移（`push`）と置き換える遷移（`replace`）を使い分ける（ログイン処理中の画面は `replace`） |

#### Next.js のスタイリング

| 観点 | 内容 |
|---|---|
| 概要 | Tailwind CSS のユーティリティクラスや CSS Modules で、コンポーネントごとにスタイルを当てる |
| 何ができるのか | クラス名だけで余白・色・文字の大きさを指定できる。`md:` のような接頭辞で画面幅ごとにレイアウトを切り替えられる（レイアウトの切り替え幅 768px は Tailwind の `md` に合わせた）。`dark:` でダークモード、`next/font` でフォントの読み込みを最適化できる |
| 気をつけること | クラスが長くなるため、ボタン・入力欄などは共通部品に閉じ込める。色や余白は設定ファイルのテーマにまとめ、画面ごとに場当たりで指定しない。**Tailwind はソースに書かれたクラスだけを生成する**ため、クラス名を文字列の連結で組み立てると効かない |

#### Next.js からの API 呼び出し

| 観点 | 内容 |
|---|---|
| 概要 | API を呼ぶ場所を、Server Components の `fetch`、Server Actions、Route Handlers、Client Components の `fetch` から選べる |
| 何ができるのか | サーバで取得すると、初期表示が速く、トークンをブラウザに出さずに済む。Server Actions でフォームの送信をサーバの関数として書ける。Route Handlers で、フロントと API の間に立つ中継（BFF）を作れる |
| 気をつけること | **`fetch` のキャッシュの既定がバージョンで違う**（Next.js 14 はキャッシュする、15 以降はしない）。登録直後に一覧へ反映させたい家計簿では、古い結果が出ないよう明示する。`fetch` は `4xx` / `5xx` でも例外にならないため、ステータスで分岐する（Step 4 でも学んだ点）。API のレスポンスを TypeScript の型で定義し、`category: null`（未分類）のような `null` の扱いを型で強制する |

#### Next.js でのログイン機能の実装

| 観点 | 内容 |
|---|---|
| 概要 | ログイン後に受け取った認証情報を Cookie に保存し、サーバ側で確認して、未ログインならログイン画面へ送る。ユーザのロールに応じて表示を出し分ける |
| 何ができるのか | ページを描く前に、認証が必要なパスへのアクセスを止められる（Next.js 16 以降は `middleware.ts` が `proxy.ts` に改名）。HttpOnly Cookie にすれば JavaScript から読めないため、XSS でトークンを盗まれにくい。Server Components で Cookie を読み、ユーザ情報を取得して描画できる |
| 気をつけること | **表示の出し分けは見た目だけで、権限の確認は必ず API でも行う**（本サービスの API は他ユーザのリソースに `404` を返し、存在するかどうかも伝えない）。Cookie の属性（HttpOnly / Secure / SameSite）と CSRF の対策。ログイン後の戻り先をそのまま使うとオープンリダイレクトになる（Step 4 判断 7）。本サービスは Google のログイン結果をフラグメントで受け取るため、Cookie 方式にするにはトークンを Next.js のサーバに渡して載せ替える処理が要る |

#### Next.js によるフロントエンドアプリケーションの実装

| 観点 | 内容 |
|---|---|
| 概要 | ルーティング・スタイリング・API 呼び出し・認証を組み合わせて、画面一覧と遷移図のとおりに動く 1 つのアプリにまとめる |
| 何ができるのか | `app/` に画面、`components/` に共通部品、`lib/` に API の呼び出しと型を置く構成で、画面と処理を分けられる。TypeScript の型チェックと ESLint でコミット前に問題を見つけられる（Step 6 の判定基準） |
| 気をつけること | **API の呼び出しを 1 か所にまとめ**、トークンの付与・`401` の処理・エラーの形の変換を各画面に書かない。`NEXT_PUBLIC_` で始まる環境変数はブラウザに埋め込まれるため、秘密を入れない。Next.js はメジャーバージョンごとに既定値や名前が変わる（`fetch` のキャッシュ、`middleware` → `proxy`、16 で `next lint` が廃止され ESLint を直接実行）ため、講座と手元のバージョンを確かめる。`next build` で初めて出るエラーがあるため、開発サーバで動くだけで済ませない |
