## 0. 画面設計で見つかった API 仕様の不足

画面一覧を作るにあたり、**各画面のボタン・入力欄が「どの API の、どのフィールドを使うか」を 1 つずつ API 仕様書と突き合わせました**。
その結果、API 仕様書だけを見ていたときには気づかなかった不足が 7 件見つかりました。

| # | 見つかった不足 | 見つけた画面 | 対応 | 実装フェーズ |
|---|---|---|---|---|
| 1 | **メール連携を始める API が無い**。ログインでは `gmail.readonly` を要求しない設計にしたが、後から許可してもらう入口を定義していなかった。`mail_accounts` を作る手段が無く、メールの取込以降がすべて始まらない | SCR-050 メール連携 | **API-029 / API-030 を追加** | 拡張 |
| 2 | **決済手段の選択肢を取得する API が無い**。API-010 / 011 / 013 は `payment_method_id` を受け付けるのに、クライアントがその ID を知る手段が無かった | SCR-010 / 011 / 013 | **API-031 を追加** | コア（Step 6） |
| 3 | **Google の同意画面で「キャンセル」するとアプリに戻れない**。API-003 がエラーを JSON で返すため、ユーザは API サーバの JSON の画面に取り残される | 画面遷移図（認証まわり） | **API-003 を変更**（エラーもフロントへリダイレクト） | コア（Step 6） |
| 4 | **取引の編集で店舗を変えられない**。API-013 は `merchant_id` しか受け付けず、店舗を選ぶための一覧（API-022）は拡張フェーズ | SCR-013 取引編集 | 店舗名は表示のみとし、**相談事項**に挙げる | - |
| 5 | **疑似重複の「相手」が分からない**。`is_possible_duplicate` は真偽値のみで、どの取引と重複しているかを API も DB も持っていない。「別の買い物です」と答える API も無い | SCR-040 重複の確認 | 記録のみ（Step 8 で設計） | 拡張 |
| 6 | **マージ解除に必要な ID が画面から分からない**。API-016 は統合元の ID を要求するが、API-012 はそれを返さない | SCR-012 取引詳細 | 記録のみ（Step 8 で設計） | 拡張 |
| 7 | **「未分類」の表し方が 2 通りある**。初期カテゴリに `未分類` があるが、Step 3 の実装ではカテゴリを選ばずに登録した取引や、カテゴリを削除した取引は `category_id = NULL` になる。さらに API-010 は `NULL` を絞り込めない。取引一覧で「未分類」を選んでも、片方しか出てこない | SCR-010 取引一覧 / SCR-020 カテゴリ管理 | **`NULL` に一本化**し、カテゴリ `未分類` は作らない。API-010 に `category_id=none` を追加 | コア（Step 6） |

**1〜3・7 は API 仕様書に反映済み**です（[step2-api-spec.md](./step2-api-spec.md) 冒頭の「画面設計による追加・変更」、5 章、6 章の API-003 / API-010 / API-029〜031）。7 は DB 仕様書（`categories.is_system`・`transactions.category_id` の説明）と Step 0 の P6（分類不能の扱い）にも反映しました。

#7 で `NULL` に一本化した理由は、**Step 3 の実装と FK（`ON DELETE SET NULL`）がすでに `NULL` 側で動いている**ためです。カテゴリ `未分類` に寄せる案（登録時・削除時にアプリ側で `未分類` を付ける）も検討しましたが、FK の挙動と食い違い、実装の変更も大きくなります。

5・6 は既存のコアのエンドポイント（API-010 / API-012）のレスポンスを変える必要があり、今変えると **Step 3 の実装と仕様書が食い違う**ため、拡張機能を実装する Step 8 で合わせて確定させます。

### API-029 / API-030 の設計で考えたこと

| 論点 | 判断 |
|---|---|
| 開始を `GET` のリダイレクト（API-002 と同じ形）にしない | 連携は「誰のメールか」を特定するため認証が必要だが、ブラウザの画面遷移では `Authorization` ヘッダを付けられない。トークンをクエリに載せるとログや `Referer` に残る。そこで **Bearer 付きの `POST` で認可 URL を受け取り、フロントがそこへ遷移する** 2 段階にした |
| コールバックでのユーザの特定 | `state` に `user_id` と**用途（メール連携）**を紐づける。用途を持たせないと、ログイン用の `state` をメール連携のコールバックに流用できてしまう |
| リフレッシュトークン | バッチがユーザ不在のまま定期的にメールを読むため、`access_type=offline` と `prompt=consent` を付けてリフレッシュトークンを必ず受け取る |
| スコープの部分拒否 | Google の同意画面はスコープ単位でチェックを外せるため、付与されたスコープに `gmail.readonly` が含まれるかを確認し、無ければ `INSUFFICIENT_SCOPE` とする |
| フロントに返すもの | 結果（成功 / エラーコード）のみ。Google の認証情報は暗号化して DB に保存するだけで、フロントには一切返さない |

> **前提**: API-029 / API-030 は、メールの取込方式を **Gmail API（OAuth）とした場合**の設計です。
> 取込方式は Step 0 の未決事項 1 のままで、GAS で取得部分だけを作る案（小山さんのご提案）を採る場合は連携の手順が大きく変わり、この 2 つは作り直しになります。
> **「連携を始める入口が無い」という不足（#1）自体は取込方式によらず存在する**ため、今回は仕様書に入口を定義したうえで、方式の確定を相談事項に挙げます。

## ③ 設計判断

### 想定するユーザ動線

**A. 初めて使う（コア）**

```
SCR-001 ルート → SCR-002 ログイン → Google の同意画面 → SCR-003 ログイン処理中
  → SCR-010 取引一覧（まだ 0 件） → SCR-011 取引登録 → SCR-010 取引一覧
```

ログインでは `openid` / `email` / `profile` のみを求め、メールの読み取りは求めない。**メール連携を許可しなくても、手入力の家計簿として最初の 1 件をすぐ登録できる**ことを優先した。

**B. 日々の記録と確認（コア）**

```
SCR-010 取引一覧（当月の合計を見る） → 絞り込み → SCR-012 取引詳細 → SCR-013 取引編集 → SCR-012
```

**C. メール連携後の日常（拡張）**

```
SCR-030 ダッシュボード → 要確認バッジ → SCR-040 重複の確認 / SCR-041 未判定メール → 解消
```

拡張後は入力をメールが自動で行うため、**ユーザの主な操作は「見る」と「直す」に変わる**。そのためホームをダッシュボードに切り替え、「直す」必要があるもの（重複・未判定・再認証）を件数バッジとバナーで目立たせる。

### 遷移設計上の判断

| # | 判断 | 理由 |
|---|---|---|
| 1 | **拡張の画面も一覧と遷移図に含め、`実装フェーズ` で区別した** | 課題が「必要な画面をすべて洗い出す」ことを求めているため。また、拡張の画面まで描いたことで 0 章の不足（特に #1）が見つかった |
| 2 | **ホームは今は取引一覧、拡張後はダッシュボード** | 月次サマリ（API-023）が拡張フェーズのため。切り替えは SCR-001 の振り分け先を変えるだけで済むようにした |
| 3 | **確認・入力のダイアログは独立した画面にしない** | URL を持たせる必要がなく、画面を移らずに完結する操作のため。画面として数えると遷移図が「開く → 閉じる」の線で埋まる |
| 4 | **登録と編集は画面 ID を分け、入力欄は共通にする** | 呼ぶ API、初期値の有無、送る項目（編集は変更した項目だけを送る）が違うため。見た目は同じでも振る舞いが違う |
| 5 | **取引一覧の絞り込み条件は URL のクエリに持つ** | 詳細から「戻る」で条件が保たれる。ダッシュボードのカテゴリ内訳や店舗管理から「条件つきの一覧」へ直接遷移させることもできる |
| 6 | **認証の扱いを全画面で共通にする** | 未ログインでの直接アクセスも、利用中のトークン切れ（`401`）も、同じく SCR-002 へ送り、開こうとしていた画面を戻り先として保存する。画面ごとに書くと漏れる |
| 7 | **戻り先は `/` で始まり `//` で始まらないパスに限る** | 戻り先に外部サイトの URL を入れられると、ログインをきっかけにしたオープンリダイレクトになる。Step 3 で `redirect_uri` を許可リストで検証したのと同じ考え方 |
| 8 | **SCR-003 でトークンを受け取ったら、すぐ URL から消す** | Step 3 でトークンを URL フラグメントで渡す設計にしたが、そのままではブラウザの履歴に残る。`history.replaceState` で消す |
| 9 | **トークンは `sessionStorage` に保存する** | `localStorage` はタブを閉じても残り続け、XSS があった場合に読まれる期間が長い。代わりに新しいタブではログインし直しになるが、Google のログインは 1 クリックで済むため許容した（相談事項 2） |
| 10 | **`404` と `403` は同じエラー画面で文言だけ変える** | API 仕様書で他ユーザのリソースを `403` と明示する方針にしたため、画面でも「存在しない」と「見られない」を区別して伝える |
| 11 | **登録後は一覧へ、編集後は詳細へ戻す** | 手入力はレシートなどをまとめて入れる場面を想定しており、一覧に戻る方が次の入力に移りやすい。編集は直した結果を確認したい |
| 12 | **フロントと API を同一オリジンで配信し、CORS は許可しない** | フロント（`localhost:5173`）から API（`localhost:8080`）を直接呼ぶと別オリジンになり、`Authorization` ヘッダ付きのリクエストはブラウザに止められる。Step 3 のバックエンドには CORS の設定が無い。開発時はフロントの開発サーバのプロキシ、クラウドではロードバランサのパスルーティングで同一オリジンにすれば、許可するオリジンを管理する必要自体がなくなる（API 仕様書 2 章に追記） |

### カバーしていない操作パターン

| 操作 | カバーしない理由 |
|---|---|
| 決済手段の追加・編集・削除 | 決済手段はメールの解析（P4）でカード下 4 桁などから自動で作る前提のため。コアの段階ではユーザ作成時の `現金` のみになる |
| 取引の編集で店舗を変える | 0 章 #4。相談事項 1 |
| 取込元のメールの本文を見る | **Step 0 では取引詳細の主な操作に挙げていたが、今回は対象外にした。** 本文を取得する API が無く、メールの全文をブラウザに出す必要性も薄い（API-017 が本文を返さないのと同じ方針）。取引詳細では抽出した結果（生の店舗名・イベント種別・金額）までを見せる |
| 未判定メールからのテンプレート作成 | Step 0 では未判定メールの画面の操作に挙げていたが、テンプレートの生成・レビューを扱う API が無く、LLM の利用可否も未決（Step 0 の未決事項 8）のため Step 8 で扱う |
| 送信元ごとの受信件数（同期状況） | Step 0 では同期状況の画面に挙げていたが、集計する API が無い。取込の途絶は最終同期日時で検知できるため、Step 8 で要否を判断する |
| 支出マップ | Step 0 の時点で任意（優先度低）としていた。API-022 が緯度・経度を返すため、追加する場合も API の追加は不要 |
| 疑似重複に「別の買い物です」と答える | 0 章 #5。Step 8 で設計する |
| 退会・アカウントの削除 | 対応する API が無い。個人の金融データを扱うため、実装するなら削除範囲（メール原本を含むか）を先に決める必要がある |
| CSV の出力、取引の一括編集・一括削除 | 最低限の家計簿としての動線に含めなかった |
| 円以外の通貨での入力 | API-011 が `JPY` のみ受け付けるため、通貨の入力欄を出さない |
| 複数タブでの同時利用 | 判断 9 のとおり、新しいタブではログインし直しになる |

## ④ まとめ

### 苦労したこと

**画面を並べるだけでは、API 一覧の書き写しになってしまうこと。** API ごとに画面を割り当てるだけでは、API 仕様書の不足は見つかりません。「この画面のこのボタンを押したら、どの API の、どのフィールドを送るのか」を 1 つずつたどったことで、0 章の 7 件が見つかりました。決済手段の件（#2）は、登録画面のプルダウンに**何を並べるのか**を考えて初めて気づきました。

**19 画面の遷移を 1 枚の図に収められなかったこと。** 共通ヘッダーからほぼすべての画面へ線が伸び、読めない図になりました。ナビゲーションで到達する経路と、画面から画面への遷移を分け、画面内で完結する操作（ダイアログ・絞り込み）は図から外して表に移すことで読める図にしました。

### 判断に迷ったこと

- **拡張の画面をどこまで描くか。** Step 6 で作るのはコアの 9 画面だけですが、拡張まで描いたことで最大の不足（#1 メール連携の入口が無い）が見つかったため、すべて描いて `実装フェーズ` で区別する形にしました
- **取引の編集で店舗を変えられるようにするか。** API-013 に店舗名を受け付けさせれば解決しますが、コアの API の仕様変更になるため、今回は表示のみとして相談事項にしました
- **トークンの保存先。** `sessionStorage` と `localStorage` のどちらにするかで、「新しいタブで開く」ときの遷移が変わります。遷移図に影響するため Step 4 のうちに決めました

### 学んだこと

**設計物は、別の視点から見直して初めて穴が見えること。** Step 3 では「実装してみると仕様書に書いていないことが出てくる」ことを経験しましたが、今回は「画面から見ると API に足りないものが出てくる」ことを経験しました。どちらも、**作った本人が同じ視点で見直しても見つからない**点が共通しています。

**穴は正常系より異常系の遷移にあること。** 見つかった不足のうち #3（Google でキャンセルすると戻れない）は、「失敗したらどの画面へ行くか」を遷移図に描こうとして気づきました。正常系の矢印だけを描いていたら見落としていました。

**画面の遷移にもセキュリティの判断があること。** ログイン後の戻り先（判断 7）や URL に残るトークン（判断 8）は、Step 3 でバックエンド側で考えたこと（`redirect_uri` の許可リスト、フラグメントでの受け渡し）をフロント側でも同じように考える必要がありました。

## メンタリング報告

### 3.1 講座の振り返り

#### HTML／CSS

| 観点 | 内容 |
|---|---|
| 概要 | HTML は文書の**構造と意味**を、CSS は**見た目**を記述する。役割を分けることで、同じ HTML に別の見た目を当てられる |
| 何ができるのか | `header` / `nav` / `main` / `form` / `table` などの要素で意味のある構造を作る。`input` の `type` / `required` / `min` でブラウザ標準の入力検証を行う。Flexbox / Grid でレイアウトを組み、メディアクエリで画面幅に応じて切り替える |
| 気をつけること | 見た目のために要素を選ばない（すべて `div` にしない）。`label` と `input` を関連づけないと、スクリーンリーダーで何の欄か分からなくなる。CSS は基本的にグローバルなため、クラス名の衝突や詳細度の競合に注意する。**ブラウザの入力検証は補助であり、サーバ側の検証の代わりにはならない**（Step 3 の `INVALID_AMOUNT` などはサーバでも必ず弾く） |

#### JavaScript

| 観点 | 内容 |
|---|---|
| 概要 | ブラウザ上で動く動的型付けの言語。DOM を操作して画面を部分的に書き換え、イベントに応じて処理を行う |
| 何ができるのか | DOM 操作による表示の更新、フォームの送信などのイベント処理、`fetch` による API の呼び出し、`Promise` / `async` / `await` による非同期処理の記述 |
| 気をつけること | **`fetch` は `4xx` / `5xx` でも reject しない**ため、`response.ok` やステータスコードを自分で判定する必要がある（問い合わせフォームの章）。送信中にボタンを無効にしないと二重送信が起きる。API から受け取った値を `innerHTML` に入れると XSS になるため `textContent` を使う。`==` の暗黙の型変換や、`0.1 + 0.2` のような浮動小数点の誤差（**金額を最小単位の整数 `amount_minor` で扱う API 設計が、ここで効いてくる**） |

#### TypeScript

| 観点 | 内容 |
|---|---|
| 概要 | JavaScript に静的な型を加えた言語。コンパイル時に型を検査し、実行時には JavaScript に変換される |
| 何ができるのか | API のレスポンスを型として定義できる。`merchant: Merchant \| null` のように null になりうることを型で表し、確認漏れをコンパイル時に検出できる。`status: 'pending' \| 'confirmed'` のようなリテラル型のユニオンで取りうる値を限定できる。エディタの補完が効く |
| 気をつけること | **型は実行時には消える**ため、API が本当に型どおりの値を返す保証はない。どこまでを信頼するかを決めておく。`any` や `as` で型検査を黙らせない。`strict` を有効にしないと null の確認漏れを検出できない。**API 仕様書と型定義が二重管理になる**ため、仕様書を変えたら型も変える運用が必要（Step 4 で API-029〜031 を追加したように、仕様は変わっていく） |
